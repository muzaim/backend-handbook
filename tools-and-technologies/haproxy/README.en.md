# HAProxy (High Availability Load Balancer)

## 1. Real-World Scenario

In a high-frequency financial technology (fintech) and crypto exchange platform, the edge network infrastructure processes over 250,000 requests per second (RPS) generated by mobile devices, institutional trading bots (HFT), and banking partner networks.

The inbound traffic profile is highly heterogeneous, demanding strict performance consistency:
- Millions of persistent WebSocket streams that must remain alive for hours to broadcast live order book market depth.
- High-velocity RESTful API requests demanding sub-2ms proxy latency paired with fair traffic distribution algorithms (*Least Connections*).
- Binary TCP socket protocols (such as ISO-8583 core financial settlement messages) operating completely outside HTTP.

If terminated by general-purpose web servers not engineered exclusively for low-level packet switching:
- Each idle or persistent TCP socket consumes substantial kernel buffer memory, causing memory thrashing.
- When an upstream Go backend node crashes under heavy load, generic load balancers lag in failure detection, returning thousands of preventable `502 Bad Gateway` errors to end users.

**Solution with HAProxy:**
The platform standardizes on an active-passive cluster of **HAProxy** instances at the network edge. HAProxy is engineered purely as a high-performance Layer 4 (TCP) and Layer 7 (HTTP) load balancer powered by an event-driven, non-blocking architecture using Linux `epoll`. A single HAProxy instance manages **hundreds of thousands of concurrent connections** with deterministic, ultra-low memory footprints. Through aggressive, sub-second *Active Health Checks*, HAProxy isolates failing Go nodes within milliseconds, redirecting user traffic seamlessly to healthy upstream servers without dropping a single in-flight request.

## 2. What Is It and What Is It For?

HAProxy (*High Availability Proxy*) is an open-source, high-performance reverse proxy and load balancer widely considered the gold standard for high-throughput network traffic distribution.

Core architectural characteristics:
- **Dual Operating Modes (Layer 4 & Layer 7)**:
  - **TCP Mode (Layer 4)**: Forwards raw binary packet streams directly without inspecting application-layer payloads (optimal for PostgreSQL/MySQL database replicas, RabbitMQ clusters, or Redis instances).
  - **HTTP Mode (Layer 7)**: Decodes HTTP headers, evaluates URI paths, manages session cookies, and handles high-throughput TLS termination.
- **Legendary Memory Efficiency**: Implements zero-copy memory buffers and a non-blocking event engine capable of processing gigabits of bandwidth with minimal CPU footprint.
- **Runtime Socket API**: Enables operations teams to dynamically alter server weights, drain traffic for zero-downtime maintenance, and inject upstream servers via a UNIX domain socket without reloading the daemon.

## 3. Why Is It Needed at High Throughput?

When measured by raw routing throughput and concurrency limits, HAProxy consistently outperforms traditional multi-purpose web servers:
1. **Network Hardware Saturation**: Capable of saturating 10 Gbps to 40 Gbps network cards with sub-millisecond proxy latencies.
2. **Comprehensive Load Balancing Algorithms**: Provides native support for *Round-Robin*, *Least Connections* (vital for varied-duration processing jobs), *Source IP Hashing*, and *Consistent Hashing*.
3. **High-Frequency Health Checks**: Performs granular HTTP, TCP, and external agent health checks to guarantee traffic is never dispatched to degraded downstream backends.

## 5. Core Configuration & Go Integration

### Production `haproxy.cfg` (Layer 7 with Active Health Checks)

```haproxy
global
    log /dev/log local0 info
    maxconn 100000          ; Accept up to 100,000 concurrent sockets
    user haproxy
    group haproxy
    daemon
    stats socket /var/run/haproxy.sock mode 660 level admin  ; Runtime Socket API

defaults
    log     global
    mode    http            ; Layer 7 HTTP Mode
    option  httplog
    option  dontlognull
    timeout connect 5000ms  ; Upstream TCP connect timeout
    timeout client  50000ms ; Client inactivity timeout
    timeout server  50000ms ; Server response timeout
    retries 3               ; Automated connection retry attempts

frontend public_ingress
    bind *:80
    bind *:443 ssl crt /etc/ssl/certs/company.pem alpn h2,http/1.1
    
    # Path-based routing using Access Control Lists (ACLs)
    acl is_order_api path_beg /api/v1/orders
    
    use_backend order_service_backend if is_order_api
    default_backend default_fallback_backend

backend order_service_backend
    balance leastconn       ; Distribute to server with fewest active connections
    option httpchk GET /healthz  ; Active Health Check probe against Go backend
    http-check expect status 200
    
    # Upstream pool with 2-second check intervals (inter 2000)
    server order_app_1 10.0.1.101:8080 check inter 2000 fall 3 rise 2 weight 100
    server order_app_2 10.0.1.102:8080 check inter 2000 fall 3 rise 2 weight 100
    server order_app_backup 10.0.1.103:8080 check backup  ; Hot standby instance
```

### Standard Health Check Handler in Go Backend

Go applications must expose lightweight `/healthz` endpoints to respond cleanly to HAProxy health monitors:

```go
package main

import (
	"database/sql"
	"net/http"
)

func HealthCheckHandler(db *sql.DB) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// Verify internal health (e.g., database reachability)
		if err := db.PingContext(r.Context()); err != nil {
			// Return non-200 to instruct HAProxy to pull this node from rotation
			http.Error(w, "Database unavailable", http.StatusServiceUnavailable)
			return
		}

		w.WriteHeader(http.StatusOK)
		w.Write([]byte("OK"))
	}
}
```

## 6. Trade-offs (Pros & Cons)

### Pros
- **Extreme Throughput & Concurrency Density**: Exceptional stability under hundreds of thousands of open connections without memory leaks.
- **Native Layer 4 & Layer 7 Versatility**: Seamlessly load balances both HTTP/gRPC traffic and raw TCP connections (databases, message queues).
- **Comprehensive Built-In Observability**: Ships with an embedded web monitoring dashboard (*HAProxy Stats Page*) and live UNIX runtime socket administration.

### Cons
- **Not a Static Web Server**: Does not serve static files (HTML, CSS, images) from local storage (unlike NGINX or Apache).
- **No Embedded Dynamic Scripting Language**: Lacks out-of-the-box scripting extensibility comparable to OpenResty/Lua in NGINX.
- **Proprietary ACL Configuration Syntax**: Configuration rules have a distinct syntax requiring dedicated operational learning.

## 7. When to Use vs When to Avoid

### When to Use
- The primary edge ingress load balancer fronting large fleets of Go microservices, gRPC backends, or WebSocket clusters.
- Layer 4 load balancing for distributed databases (PostgreSQL Read Replicas, MySQL Galera) or RabbitMQ broker clusters.
- Infrastructures with immense volumes of persistent long-lived TCP connections.

### When to Avoid
- Simple static website asset delivery where standard NGINX or CDNs are superior.
- Complex API Gateways requiring dynamic payload transformations via JavaScript/Lua (e.g., Kong or Apache APISIX).
- Basic single-instance monoliths lacking upstream server pools.

## 8. Key Observability Metrics (Monitoring Dashboard)

- **`haproxy_frontend_current_sessions` (Gauge)**: Total active client connections handled by the frontend listener.
- **`haproxy_backend_response_time_average_seconds` (Gauge)**: Average upstream server response time.
- **`haproxy_server_status` (Gauge: 1=UP, 0=DOWN)**: Operational health status per node. Immediate alert trigger if instances enter a DOWN state.
- **`haproxy_backend_current_queue` (Gauge)**: Requests queued waiting for an available backend slot; values above 0 indicate downstream saturation.

## 9. Real-World Case Studies

### Balancing 300,000 Persistent TCP Connections and Sub-Second PostgreSQL Database Failover

- **The Engineering Problem**: A real-time gaming and financial transactions platform maintained hundreds of thousands of long-lived WebSocket connections alongside a high-throughput PostgreSQL cluster (1 Primary and 4 Read Replicas). The infrastructure initially relied on standard cloud DNS load balancers. When the primary database suffered an abrupt hardware node crash, DNS cache propagation took over 60 seconds to converge, causing thousands of application queries to pound the dead primary with catastrophic cascading write errors. Furthermore, the generic cloud proxy frequently dropped persistent WebSocket connections due to connection state saturation.
- **The Architectural Solution**: The infrastructure team deployed an active-passive *HAProxy* cluster (managed with Keepalived VRRP) providing dedicated Layer 4 TCP and Layer 7 proxying. For the PostgreSQL fleet, HAProxy operated in TCP mode with health-checking probes polling Patroni cluster agents (`http-check expect status 200`). When Patroni elected a new primary during node failure, HAProxy dynamically redirected write traffic to the newly promoted primary in under 500 ms without waiting for DNS propagation. For the WebSocket fleet, HAProxy configured `timeout tunnel 3600s`, `maxconn 150000`, and optimized OS network socket parameters.
- **The System Outcome**: Database failover Recovery Time Objective (RTO) dropped from 60 seconds to under 1 second with zero dropped write transactions. HAProxy sustained 300,000 concurrent long-lived TCP connections with CPU utilization remaining under 12%. Random client socket drops decreased by 99.9%, establishing unbroken real-time gameplay and financial trade streams.

## 10. Production Gotchas

1. **Operating System File Descriptor Limits (`ulimit -n`)**: Setting `maxconn 100000` in HAProxy while leaving the Linux system limit at default (often 1024). HAProxy crashes immediately once connections reach 1024.  
   *Mitigation*: Increase `fs.file-max` and set `/etc/security/limits.conf` to a minimum of 250,000 file descriptors.
2. **Reloads Dropping Active Connections**: Executing standard system service reloads (`systemctl reload haproxy`) with active long-lived WebSocket connections, causing immediate disconnects.  
   *Mitigation*: Enable *Seamless Reloads* (using the `-x` socket transfer flag) to gracefully hand off listening sockets to new processes.
3. **Static DNS Caching**: HAProxy resolves upstream DNS hostnames at boot time by default. In dynamic cloud environments (AWS ELB / Kubernetes), failing to configure the built-in `resolvers` block causes HAProxy to route to decommissioned IPs.

## 11. Key Takeaways

- **High-Performance Dedicated L4 & L7 Proxy**: HAProxy is engineered exclusively for ultra-low latency, high-throughput network proxying and balancing across HTTP, gRPC, WebSocket, and raw TCP protocols.
- **Advanced Health Checking Heuristics**: HAProxy performs granular active health checks (TCP handshakes, HTTP status codes, payload regex matches) to detect and isolate degraded backends in milliseconds.
- **Enforce Seamless Process Reloads**: Deploy configuration reloads using the `-x` socket transfer mechanism to migrate listening sockets to fresh processes without severing established long-lived connections.
- **Pure Load Balancer, Not a Web Server**: HAProxy does not serve static files from storage; pair HAProxy with NGINX or CDNs to serve static web assets.
